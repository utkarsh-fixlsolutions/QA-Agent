# Phase B Part 5 — Live Reporting

**Status:** Confirmed
**Date:** 2026-09-05

Watch mode now reads as a continuous monitoring stream rather than a series of independent CLI reports. Presentation only — the pipeline is untouched.

## What a batch looks like
```
--------------------------------------------------
Batch #2   15:40:51

Files changed:
  - src\model.py (created)
  - src\recognize.py (created)

Findings (1):
  ...\src\recognize.py:1  [error] F401: `os` imported but unused  (ruff)
```
A clean batch ends in `Findings: no issues found.`; a deletion-only batch ends in `Nothing to analyze.` — a header is never left dangling.

Event kind is annotated only when it adds something: `(deleted)`, `(renamed from x.py)`, `(created)`. A plain modification needs no label.

## Part 5 removed as much as it added
The point was not simply to add a header. Each report previously repeated what a header would now state:

| Previously printed every batch | Why it is gone |
|---|---|
| `Run at: <timestamp>` | the batch header carries the time |
| `Input: watch: 3 changed files` | the header lists the actual files |
| `Checked: 3 file(s)` | the count of that same list |
| `Tools: ruff` | constant forever; already in the startup banner |

That is requirement "avoid printing duplicate information" taken literally. Watch mode prints the batch header plus the findings, and nothing twice.

## `render_findings()` — the one renderer change
`report.py` gained `render_findings(result)`; `render(result, source)` is now *summary block + the same lines*. Both share `_findings_lines()`, so **there is exactly one implementation of findings formatting**.

**One-shot CLI output is byte-identical.** Verified, not assumed: golden outputs were captured *before* the refactor and diffed after — findings, clean, directory-with-skipped, missing-path, and the Markdown file all came back `IDENTICAL`.

## The bridge became pure orchestration
Rather than injecting a renderer, `AnalysisBridge.analyze_paths(paths)` now **returns an `AnalysisOutcome`** and prints nothing. The reporting layer decides how to show it.

```python
@dataclass(frozen=True)
class AnalysisOutcome:
    result   # RunResult on success
    error    # the exception on failure
    expected # True for an anticipated ToolError, False for anything unforeseen
```
Classifying the failure is orchestration's job — it caught the exception. Formatting it is not.

The proof this was the cleaner option is the dependency graph: the bridge now imports **only** `run` and `ToolError`. It no longer imports `report`, `watch`, or `fsmonitor`.

**`AnalysisBridge.__call__(event)` was removed.** It had been dead since Part 4 (the debouncer calls `analyze_paths` directly), and it printed an echo and a report — exactly the presentation being moved out. Keeping it would have left two contradictory contracts in one class.

## Module layout
| File | Change |
|---|---|
| `qa_agent/live_report.py` | **new** — `LiveReporter`, batch identity, file lists, `display_path()` |
| `qa_agent/analysis_bridge.py` | returns `AnalysisOutcome`; prints nothing; `__call__` removed |
| `qa_agent/report.py` | added `render_findings()` via a shared `_findings_lines()` |
| `qa_agent/watch.py` | presentation helpers removed — now **lifecycle only** |
| `qa_agent/__main__.py` | wires reporter + bridge into the flush callback |
| `fsmonitor.py`, `debouncer.py`, `runner.py`, `adapters.py` | **untouched** |

`watch.py` now imports only `sys`, `threading`, and `pathlib`, and defines exactly one class. That is what Part 1 asked for and Part 5 finally delivered — `print_file_event`, `print_change_summary`, and `describe_batch` were never `WatchSession`'s job.

## Where each responsibility lives
- **Batch numbering** — `LiveReporter` instance state; survives for the session, resets on restart (no persistence).
- **Timestamps** — generated by `LiveReporter` at print time; the moment the batch is reported.
- **File-list formatting** — `LiveReporter`.
- **Findings formatting** — `report.py`, unchanged owner.
- **Batching** — `Debouncer`. **Orchestration** — `AnalysisBridge`. **Lifecycle** — `WatchSession`. All unchanged.

`report.py` never learns what a batch is; `live_report.py` runs nothing.

## Two deliberate choices
**Long batches are capped at 10 files** with `...and N more`. A `git checkout` can change hundreds of files and would otherwise bury the findings. **Presentation only — every changed file is still analyzed**, which the remainder count keeps honest.

**Output is pure ASCII.** Bullets (`•`) and ellipses (`…`) would raise `UnicodeEncodeError` when watch output is redirected to a file on a cp1252 Windows console — the same class of bug hit earlier in this project. A crash in a process meant to run for hours is not worth a prettier bullet. Verified by asserting every output byte is ASCII.

**End-to-end, live watcher (12/12):** every batch carries an identity and timestamp · numbering sequential across batches · each batch separated by a rule · each lists its triggering files · multi-file batches list all of them · clean batches say so plainly · deletions annotated and not analyzed · a 14-file batch capped with `...and 4 more` · **no `Run at:` / `Input:` / `Checked:` duplication** · `Tools:` never repeated · findings still carry real rule codes · **output is entirely ASCII**.
