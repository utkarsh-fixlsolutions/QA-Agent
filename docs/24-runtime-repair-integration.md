# Step 24 — Phase G Part 4: Runtime Failure -> Verified Repair Integration

**Status:** IMPLEMENTED (2026-09-11).
**Phase:** G, Part 4 — the first phase that lets an AI-diagnosed runtime failure (Phase G Part 3) become a real, applied repair, entirely through Phase E's existing verified-repair pipeline. No second repair engine, workspace, validator, decision policy, or apply mechanism exists anywhere in this phase.
**Scope:** two new public entry points in `qa_agent/ai/` — `repair_runtime_failure(check_result, diagnosis, execution_result, repository_context, provider, root, runtime_check=None, ...)` (singular) and `repair_runtime_failures(execution_result, diagnoses, repository_context, provider, root)` (plural) — plus the deterministic eligibility gate and target-localization functions they build on. Real writes are opt-in (`discover --repair-runtime`, implying `--diagnose`); `--diagnose` alone never modifies a file.

## The central principle, restated because this phase's whole purpose is to test it

AI proposes. Deterministic systems verify. Only verified repairs are applied. Concretely: a `RuntimeDiagnosis` marked `DIAGNOSED` is treated as a hypothesis, never as proof — this phase's own dogfooding (below) produced a real, structurally valid, well-grounded diagnosis that named the same real file two different ways in `affected_files`, which the deterministic eligibility gate correctly refused rather than guessing which one was meant. `ACCEPTED` and `VERIFIED` are two different, never-conflated things: `ACCEPTED` means a deterministic decision approved a candidate; only `VERIFIED` means the real, original runtime check actually passed after a real repository write.

## Why decide_repair()'s own verdict is not sufficient on its own here

Phase E Part 4's `decide_repair()` is reused completely unmodified — but its "target resolved" signal is computed from a `Finding`-shaped match key that includes `.tool`, and this phase's `RepairProposal.finding` is never a real `adapters.Finding` (there is no static-analysis finding for "the process crashed at startup"). Its `.tool` is fixed to a sentinel (`"runtime-diagnosis"`) no real analyzer ever produces, which makes `target_resolved` structurally always `True` — real, but degenerate: `decide_repair()`'s outcome for a runtime repair collapses to "did the file's own static findings improve/stay unchanged/worsen," which is real information (a static regression is always vetoed) but not the real question ("did the runtime problem get fixed"). This is stated plainly in `runtime_repair.py`'s own module docstring rather than left implicit.

The fix: `decide_repair()`'s own verdict is used as a **static-regression guard only** — a `worsened` verdict always vetoes a candidate outright, unconditionally. When it doesn't veto, and a real originating `RuntimeCheck` is known, the candidate patch is materialized into a runnable copy and the *actual runtime check* — `npm run build`, not a linter — is re-run against it, inside the same Phase E Part 2 `TemporaryWorkspace`. That real runtime outcome, not `decide_repair()`'s "improved" branch, is what actually decides ACCEPT vs REJECT for a runtime repair (`_combine_decision`). When no runtime check is known or materialization isn't possible, this phase falls back to `decide_repair()`'s own verdict, honestly — it never claims a runtime-level confirmation it did not actually obtain.

## The deterministic eligibility gate — no AI decides this

`check_repair_eligibility()` refuses, never guesses, for every case Phase G Part 3's own review flagged as unsafe to act on automatically: `diagnosis_status` anything other than `DIAGNOSED` (`INSUFFICIENT_CONTEXT`/`INVALID_RESPONSE`/`AI_ERROR`/`NOT_APPLICABLE` all refused unconditionally), no cited evidence, no actionable recommendation, no affected file, more than one affected file (never arbitrarily picks one), a file that does not exist, or a file that resolves inside a generated/dependency path (`node_modules`, `.git`, `dist`, `build`, `.venv`, and the rest of `runner.py`'s own `IGNORED_DIRS` — reused directly, the same one-directional "read one plain constant" precedent `qa_agent/project/discovery.py` already established, applied a third time) or a known lockfile name.

## Deterministic target/line localization — no invented line numbers

`resolve_repair_target()` is the bridge this phase's own instructions explicitly required: never `diagnosis.affected_files[0]` handed straight to Phase E. Once exactly one real, safe file is resolved, `_locate_line()` searches that file, literally, for a real evidence token already present in the diagnosis (`affected_components`, the originating `RuntimeCheck`'s `required_evidence`, or a quoted substring pulled from the check's real reason/exception/logs/evidence) — the same "structural, not a fact-checker" discipline `diagnosis_parser.response_is_grounded` already established. A real match anchors the target line; no match anchors at line 1, explicitly marked `localized=False` so a caller can never mistake an anchor for a real match. Never a fabricated line number either way.

## A new prompt, the same response contract

`runtime_repair_prompts.build_runtime_repair_prompt()` is a new prompt builder — `build_repair_prompt` (Phase E Part 1) only ever renders a bare `Finding` plus surrounding code, which cannot carry runtime evidence (check status, captured output, the full `RuntimeDiagnosis`). What *is* reused, verbatim: the exact JSON response schema `build_repair_prompt` already requests (`explanation`/`replacement`/`confidence`/`start_line`/`end_line`), so `validate_repair_response` (Phase E Part 1's own validator, completely unmodified) parses this new prompt's response exactly as it parses any other repair proposal. No new schema, no new parser, anywhere in this phase.

## Candidate materialization — the real technical center of this phase

Phase E Part 2's `TemporaryWorkspace` is used unmodified, but its own established convention (copy only the touched file, "never the whole project") is not enough on its own to *run* a real build/test/server command, which needs the whole project tree (`package.json`, `node_modules`, everything) to even start. `_mirror_with_patch()` solves this cheaply: it recreates the real project directory tree inside the workspace using directory-entry links (a symlink, falling back to a hardlink for a plain file, falling back to a real copy only as a last resort) for every entry *except* the one file on the path to the repair target, which is written for real as the patched bytes — a distinct file the real repository is never opened for writing under. Only the directories actually on the path to the target are ever created for real; a large `node_modules` next to the target is a handful of cheap links, not a slow, wasteful copy. If linking fails at any step (an environment without symlink privilege and no same-volume hardlink), the whole mirror is abandoned (never a partial, untrustworthy one) and this phase falls back honestly to static-only validation for the candidate stage — the mandatory real post-apply check is unaffected either way.

## Bounded, no loop, no second engine

`repair_runtime_failure()` makes at most one proposal, one workspace application, one static validation, one candidate runtime check, one decision, one real apply, one final re-verification — never retried, never re-proposed, matching this phase's own explicit `max_attempts = 1`. `repair_runtime_failures()` calls it exactly once per diagnosed failure (skipping `NOT_APPLICABLE` diagnoses entirely — nothing to repair for a check that was never even sent to the AI), with the same per-check execution isolation every prior phase's own engine already uses. Every write anywhere in this phase is Phase E's own: `apply_repair` (Part 2, workspace only) and `apply_verified_repair` (Part 5, the real repository, only for an `accept_candidate` decision, only after re-verifying every precondition against the file's current state) — confirmed directly: this module's own source contains exactly one `.write_bytes(` call (inside `_mirror_with_patch`, always targeting a path inside the temporary workspace) and zero `.write_text(` calls anywhere.

## Dogfooding, real output, real live Ollama (`qwen2.5:0.5b`), no fabricated results

**A real, controlled fixture** (`build.js` calling an undefined `calculateTotal()`, a genuine `ReferenceError` crash, not staged):

- **`MockProvider`, full pipeline, real subprocesses throughout:** a real `DIAGNOSED` diagnosis fed into `repair_runtime_failures` produced a genuinely **`VERIFIED`** result — real target localization (`build.js`, line 2, the actual line naming `calculateTotal`), a real candidate materialization and real `npm run build` re-run against it (genuinely `pass`), a real write to the real file with a real backup file on disk, and a real post-apply `npm run build` re-run that genuinely passes. This is a real, end-to-end verified runtime repair, not a simulated one.
- **Real live Ollama, diagnosis stage:** consistent with Phase G Part 3's own documented findings for this small model — several attempts returned `INVALID_RESPONSE` (malformed JSON, a non-list `evidence` field). One attempt produced a real, well-grounded `DIAGNOSED` result (confidence 0.90) that named the same real file two different ways in `affected_files` (`"build.js"` and the full absolute path) — the deterministic eligibility gate correctly refused it as ambiguous rather than picking one, a genuine, useful example of the "no guessing" rule catching a real model quirk. A second attempt produced an unambiguous `DIAGNOSED` result that the eligibility gate correctly accepted and correctly localized to line 1 (no evidence token matched a specific line, honestly anchored, not invented).
- **Real live Ollama, repair-proposal stage:** one attempt against that unambiguous diagnosis returned a malformed response, correctly rejected (`PROPOSAL_FAILED`, never a crash, never a fabricated proposal). A second attempt returned a *structurally valid* proposal (confidence 1.0) whose actual replacement text and line range (`7-10`, on a 5-line file) would not plausibly have produced a working build — exactly the scenario this phase's own architecture exists to catch: it was never blindly trusted, and would have failed deterministic validation (an out-of-range line range fails at the workspace-apply stage) rather than ever reaching a real write.

## Bugs discovered during dogfooding, and how

One real bug in this phase's own logic, found by dogfooding, not by inspection: an early version of `_combine_decision()` computed the *correct* final action (override an `accept_candidate` verdict onto a static `hold` when the real runtime candidate check passed) but never propagated that override onto the actual `RepairDecision` object handed to `apply_verified_repair()` — which reads `decision.action` directly and correctly refused a decision whose `action` field still said `"hold"`. Fixed by `_effective_decision()`, which builds the one `RepairDecision` this phase actually acts on (via `dataclasses.replace`, never a hand-built object) whenever `_combine_decision()`'s verdict differs from `decide_repair()`'s own — caught immediately by the first full happy-path dogfooding attempt, before this suite of tests was even complete, and confirmed fixed by every real end-to-end run since.

## Explicit confirmations

- **AI never writes a file directly** — confirmed by direct source inspection: `runtime_repair.py` contains exactly one `.write_bytes(` call (inside `_mirror_with_patch`, a workspace-only patched copy) and zero `.write_text(` calls; every real-repository write is Phase E's own `apply_verified_repair`, called only through the injectable `apply` parameter (default: the real, unmodified function).
- **Deterministic validation remains authoritative** — the AI's own `confidence`/`explanation` are never read by any decision logic; `decide_repair()` (Phase E Part 4, unmodified) and the real runtime candidate re-check (Phase G Part 2's own executor, unmodified) are the only two inputs `_combine_decision()` ever reads.
- **`DIAGNOSED` is never proof** — demonstrated concretely, not just asserted: a real, well-grounded, high-confidence diagnosis was still correctly refused (ambiguous file naming) by the deterministic gate during dogfooding.

## Deferred to a future phase

Multi-attempt/retry repair (explicitly out of scope — `max_attempts = 1` is a hard rule, not a default to be raised later without a new phase); an approval/review UI between `ACCEPTED` and the real apply (this phase's own CLI workflow applies automatically once accepted, matching its own specified `--repair-runtime` behavior); repairing a check whose failure is genuinely external infrastructure (no dedicated detector for this beyond the generated/dependency-path denylist); executors for the 14 still-`NOT_IMPLEMENTED` check types (unchanged from Phase G Part 2 — a diagnosis, and therefore a repair, can only ever exist for the five checks that are actually implemented); any autonomous, multi-step, or multi-agent orchestration.
